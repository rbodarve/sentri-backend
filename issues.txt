ISSUES — root-cause analysis from fastapi/traces.jsonl (first 4 queries)
========================================================================

Corpus ground truth (the manifest): 6 contracts / locations
  Tubao, La Union · San Carlos, Pangasinan · Cabatuan, Isabela ·
  Sta. Fe, Nueva Vizcaya · Bulakan, Bulacan · Olongapo City

The four traces
  #1 "list me locations you have knowledgeb about"        route=simple    25s
  #2 "list me all projects you know about in launion"     route=fanout   247s
  #3 "can you change that to table format"                route=transform  6s   (correct — no issue)
  #4 "can you list me all locations you have knowledge about" route=simple 56s


------------------------------------------------------------------------
ISSUE 1 — "in launion" fans out over the ENTIRE corpus (trace #2)
------------------------------------------------------------------------
Symptom
  A location-scoped request ("projects in La Union") ran for 247s, decomposed
  into 6 parts (one per contract in the whole corpus), 3 of 6 sub-answers
  failed verification (ok=False), and the final answer listed projects that
  are NOT in La Union. The location constraint was silently dropped
  (route event: contract_ids=[]).

Data flow (where the value goes wrong)
  1. classify() — rag/agent.py:139-145 — matches _EACH_RE ("all ... projects")
     with no explicit id, so it tries to restrict scope to the named location:
         location_ids = self._rag._resolve_contract_ids(question)
         scope = sorted(location_ids) if location_ids else sorted(self._known)
  2. _resolve_contract_ids() — rag/generate.py:120-127 — matches manifest
     tokens against the query with a WHOLE-WORD regex:
         re.search(rf"\b{re.escape(tok)}\b", low)
     The manifest yields the token "union" (and "la" is dropped, <4 chars).
  3. The query contains "launion" (no space). \bunion\b does NOT match inside
     "launion": between 'a' and 'u' both chars are word chars, so there is no
     word boundary. => location_ids = empty set.
  4. Empty => scope falls back to sorted(self._known) = ALL 6 contracts =>
     kind="fanout" over the whole corpus.

REAL ROOT CAUSE
  Location resolution is whitespace/tokenization-brittle. A multi-word place
  written without its space ("launion" for "La Union") tokenizes to nothing
  the resolver indexed, so the location filter resolves to empty and the code
  fails OPEN to the entire corpus. It is not a router bug and not an LLM bug —
  the scope filter never engaged because the surface form didn't match.

SOLUTION
  Make location resolution robust to spacing so multi-word place names match
  when concatenated. In _resolve_contract_ids (rag/generate.py), match against
  a despaced/normalized form of the question as well as the plain form, e.g.
  compare tokens against low AND low with spaces removed:
      low = question.lower()
      squ= re.sub(r"\s+", "", low)
      ... match tok in low (word-boundary) OR tok in squ (substring) ...
  Index multi-word phrases too (e.g. "launion" from "la union") so the joined
  form is a first-class key. Keep the >=4-char / stoplist guard to avoid noise.
  Verify trace #2's query now resolves to the single La Union contract and
  routes simple, not fanout.

ISSUE 2 — "list all locations" is nondeterministic and lossy (traces #1 vs #4)
------------------------------------------------------------------------
Symptom
  #1 and #4 are the SAME intent yet produce different answers:
    #4 -> 6 clean, distinct locations (correct).
    #1 -> 5 lines, and it CONFLATES two provinces onto one line:
          "Barangay Luzon, Cabatuan, Isabela (Bulakan, Bulacan)".
          Isabela and Bulacan are separate contracts — a fabricated merge.
  #1's citations covered only 3 of 6 contracts; #4's covered all.

Data flow (where the value goes wrong)
  1. classify() routes both to "simple".
  2. The simple route answers via RagAnswerer: retrieve+rerank top-k chunks,
     inject the manifest node, and hand the whole context to the LLM to
     summarize into prose.
  3. The retrieved top-k chunks DIFFER by phrasing ("knowledgeb about" vs
     "all locations"), so the context the LLM summarizes differs run to run.
  4. The LLM freely summarizes that context. Even at temperature 0.0 the
     OUTPUT differs because the INPUT (retrieved context) differs, and free
     summarization can merge/drop entries.

REAL ROOT CAUSE
  A question whose complete answer IS the manifest ("list all locations /
  all projects") is being answered by free-form LLM summarization over a
  retrieval-dependent context, instead of by deterministic enumeration of the
  manifest. Retrieval variance + summarization = lossy, unstable, non-
  reproducible answers to a question that has one exact, corpus-wide answer.

SOLUTION
  Route corpus-wide "list all X" questions to a deterministic manifest
  enumeration, not LLM summarization:
    - Add a light intent test (e.g. reuse _EACH_RE / a "list all locations|
      projects|contracts" cue with no location and no explicit id).
    - Answer directly from load_manifest(): emit one row per contract from the
      manifest's own location/contract_name fields (dedupe by contract_id).
    - The LLM, if used at all, only formats a fixed list it cannot add to or
      merge (aggregation/enumeration stays deterministic, consistent with the
      "LLM never computes" principle).
  This makes #1 and #4 return the identical, complete 6-location list and
  removes the Isabela/Bulacan conflation.

The traces

  #7  "give me details about the Contract Flood Control Project along aringay river" simple 34s

  #11 "can you give me projects you know about in isabela?"             simple    32s
  #12 "can you change that to table format"                            transform  9s
  #13 "can you give me all signatures for the flood control project in macanao creek?" simple 41s

These 9 confirm Issues 1 & 2 and surface two more real root causes.


CONFIRMS ISSUE 1 (surface-form-brittle location resolution) — and generalizes it
  #5 is trace #2's question written correctly, "La Union" WITH the space. It
     resolves to the single contract 24A00153 and routes "simple" in 27s —
     exactly the behaviour #2 should have had. Same intent, one keystroke
     apart (space), completely different path. This is direct proof that #2's
     4-minute fanout was caused by the resolver, not the router or the LLM.
  #13 is the SAME failure by a different surface form: "macanao" (plain n).
     The resolver indexes "macañao" (its token regex keeps ñ), so "macanao"
     never matches, contract_id resolves to None, retrieval runs UNFILTERED,
     and it pulled a foreign contract's signatory chunk (24CC0265/SIGNATORIES)
     into context alongside the right one. It happened to answer correctly,
     but the contract filter silently failed open again.

  REAL ROOT CAUSE (broader than first stated): entity resolution matches raw
  manifest tokens with word boundaries and exact diacritics, so ANY variant —
  missing space ("launion"), dropped/changed diacritic ("macanao"), or a minor
  misspelling — fails to resolve, and the system fails OPEN (whole-corpus
  fanout, or unfiltered retrieval that can mis-bind across contracts).

  SOLUTION (extends Issue 1's fix): normalize BOTH sides before matching —
  lowercase, strip diacritics (ñ→n), and remove spaces/punctuation — and index
  the normalized keys (incl. joined multi-word phrases like "launion"). One
  normalization step fixes #2 and #13 together.


CONFIRMS ISSUE 2 (nondeterministic "list locations")
  #10 is a THIRD phrasing of "list locations" (after #1 and #4) and produces a
  THIRD formatting: 6 lines but with redundant self-parentheticals —
  "Barangay Luzon, Cabatuan, Isabela (Cabatuan, Isabela)",
  "Sta. Fe, Nueva Vizcaya (Nueva Vizcaya)", "Olongapo City (Olongapo)".
  Three runs of one corpus-wide question, three different outputs. Reinforces
  the fix: enumerate the manifest deterministically instead of summarizing it.


ISSUE 3 (new) — the "transform" route can't fetch new facts (#8)
  Symptom
    #8 "give me all signatories for that project" routed "transform" and
    REFUSED: "The previous answer does not contain any information about the
    signatories...". #9 asks for the same signatories but NAMES the project
    (no "that"), routes "simple", and succeeds (returns Esquejo & Jucar).
    The signatories existed the whole time; the follow-up just couldn't reach
    them.
  Data flow
    The transform route reworks ONLY the text of the previous answer. #7's
    prior answer was a details block with no signatories, so transform had
    nothing to reformat and (correctly, for a text op) reported none. It has
    no path to carry the already-resolved contract (24A00153) into a fresh
    retrieval.
  REAL ROOT CAUSE
    "transform" is being used for two different follow-up kinds: (a) present
    the SAME facts differently (reformat/table — legitimate, see #12), and
    (b) ask for NEW facts about the SAME entity ("signatories for that
    project"). (b) needs retrieval, not text rework, but is misclassified as a
    text transform.
  SOLUTION
    Restrict transform to presentation-only edits. A follow-up that requests
    new information about the prior entity must resolve the carried-over
    contract_id from session context and run a scoped "simple" retrieval on it
    — i.e. rewrite "signatories for that project" to "signatories for contract
    24A00153" and retrieve, rather than reformat stale text.


ISSUE 4 (new) — the real contract_id is never surfaced; the project name is
mislabeled as "Contract ID" (#5, #7, #11, #13)
  Symptom
    Every details/answer block prints "Contract ID: Flood Control Project
    along Aringay River, Tubao, La Union" (or the Macañao title). That is the
    project NAME/location, not the contract id. The true id (24A00153,
    24BG0272, ...) — which routing already knows and filtered on — is never
    shown to the user.
  Data flow
    classify()/route resolves the real contract_id and uses it to build the
    metadata FILTER, but that id is not injected into the generation context.
    The LLM sees only pdf/source names and manifest prose, so it fabricates a
    "Contract ID:" line from the project title.
  REAL ROOT CAUSE
    The resolved contract_id is a routing/retrieval-only value; it never
    reaches generation, so the model has no id to print and invents one from
    the title.
  SOLUTION
    Inject the resolved contract_id into the generation context (or
    deterministically post-fill the "Contract ID" field from the routed id).
    The id is known and exact — do not let the LLM guess it.


CORRECT BEHAVIOUR (no issue) — and one transform-quality note
  #9  scoped signatory question (named project) — resolved 24A00153, answered.
  #11 "projects in isabela" — "isabela" is a clean single token, resolved to
      24BG0272, answered (aside from the Issue-4 id mislabel).
  #12 reformat-to-table over #11's already-structured field block — clean
      table. Contrast #6: the same transform over #5's single prose blob
      MANGLED it into nonsensical one-phrase-per-row items. Transform quality
      depends on whether the prior answer was structured; folding Issue 4's
      structured fields into every answer would also make transforms reliable.

ADDENDUM 2 — final query in traces.jsonl (#14)
========================================================================

The trace
  #14 "list all projects in the database"                    fanout   165s

CONFIRMS ISSUE 2 (corpus-wide "list all X") — and adds a routing-inconsistency
and cost dimension
  Symptom
    #14 is the "list all projects" sibling of the "list all locations" family
    (#1/#4/#10). Its complete answer IS the manifest — 6 contracts. But where
    #1/#4/#10 routed "simple", #14 routed "fanout": it decomposed into 6 parts
    and ran a full retrieve+rerank+generate sub-answer PER contract (all 6
    ok=True, combine ok), taking 165s. Same enumeration intent, a fourth
    surface form, a THIRD distinct route (simple vs fanout), and by far the
    most expensive path.
  Data flow (where the value goes wrong)
    1. classify() — rag/agent.py — matches _EACH_RE ("all ... projects") with
       no explicit id and no resolvable location ("the database" resolves to
       nothing), so scope falls back to sorted(self._known) = ALL 6 contracts.
    2. That non-empty 6-id scope routes "fanout" (contrast Issue 1's #2, where
       the same empty-location fallback also fanned out). Fanout issues one LLM
       sub-answer per contract, then combines.
    3. The answer happened to come out complete and distinct (all 6, no
       Isabela/Bulacan merge), so fanout is "accidentally correct" here — but
       only by brute-forcing 6 generations for a question with one exact,
       already-materialized answer.
  REAL ROOT CAUSE
    Same as Issue 2: a question whose complete answer IS the manifest is being
    answered by the LLM route instead of by deterministic manifest enumeration.
    #14 shows the intent isn't even routed consistently — "list all locations"
    → simple, "list all projects in the database" → fanout — so the same
    corpus-wide enumeration lands on different paths with different cost
    (seconds vs 165s) and different completeness run to run.
  SOLUTION
    Issue 2's fix covers #14: detect corpus-wide "list all locations|projects|
    contracts" (no location, no explicit id) BEFORE routing, and answer by
    enumerating load_manifest() deterministically (one row per contract_id) —
    never simple summarization, never a 6-way fanout. This collapses #14 from
    165s/6-generations to a single deterministic manifest dump and makes the
    whole "list all X" family (#1/#4/#10/#14) return the identical complete
    answer by the same path.

CONFIRMS ISSUE 4 (contract_id never surfaced)
  #14's rows are titled "Contract Flood Control Project along Aringay River,
  Tubao, La Union" etc. — project names, not ids. The routed ids (24A00153,
  24AJ0052, 24BG0272, 24BJ0005, 24CC0265, 24CM0001 — all present in the
  subanswer stage events) are known and filtered on, yet none is shown. Same
  fix: inject/post-fill the resolved contract_id into the output.
