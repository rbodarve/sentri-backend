ISSUES, BY SEVERITY
-------------------

F1 - HIGH (architecture) [FIXED — wired up]: Step 3's output is never consumed.
   relationships.py builds PREV/NEXT chains, and index.py:118 runs
   link_reading_order at build time -- but nothing reads those relationships
   back. Grep across rag/ and fastapi/ finds no PrevNextNodePostprocessor, no
   AutoPrevNextNodePostprocessor, no relationship traversal at retrieval. The
   module docstring promises "this gives later retrieval a reliable way to
   expand a hit to its neighbouring blocks" (relationships.py:9) -- that
   expansion does not exist. The whole stage is inert scaffolding: it runs,
   persists edges into the docstore, and no query path touches them.
   Resolution is a fork: either WIRE IT UP (add a PrevNextNodePostprocessor
   into the retrieval path in generate.py -- small, and it would finally cash in
   the neighbor-expansion idea), or ACKNOWLEDGE it as unused and stop implying
   retrieval uses it. Right now it is the one part of Partition 1 that costs
   build work and buys nothing. (Flag, do not delete.)
   RESOLVED: took the WIRE-IT-UP fork. rag/generate.py now builds a
   PrevNextNodePostprocessor (docstore, num_nodes=1, mode="both") in
   RagAnswerer.__init__ and applies it in answer_once() right after rerank
   (nodes = self._neighbors.postprocess_nodes(nodes)), before the manifest/id
   nodes are prepended. Each hit now reaches the LLM with its immediate reading-
   order neighbours (a table row gains its header, a split answer its
   continuation). Applied ONLY on the generation path, not the recall retriever
   in evaluate.py, so make eval is untouched by construction. The neighbour edges
   themselves are regenerated on the next `make build` (they live in the
   docstore); the wiring consumes whatever edges the last build persisted.

F2 - MEDIUM (integrity/logic) [FIXED]: UNKNOWN enrichment degrades silently and
   is not gated by `make build`.
   contract_id_from_source / doc_type_from_source return the sentinel "UNKNOWN"
   on no match (enrich.py:58, enrich.py:66). The ONLY thing that catches it is
   the assertion in enrich.py's __main__ (i.e. `make check`) -- and `make build`
   does NOT depend on `check` (separate Makefile targets). So a newly added or
   renamed pdf_source that misses CONTRACT_ID_RE or DOC_TYPE_KEYWORDS silently
   collapses into a single UNKNOWN contract bucket; the retrieval filter then
   mis-scopes with no error raised.
   Note the inconsistency with F1's praise: the loader fails LOUD on bad data,
   but enrichment fails SOFT on underivable data -- opposite integrity postures
   for the same authoritative corpus, and this half is the retrieval-
   correctness-critical one. Minimal, root-cause-aligned fix: have enrich_nodes
   raise on UNKNOWN (or make `build` assert it), converting silent degradation
   into a loud failure consistent with the verify.sh philosophy. Small surgical
   change, not a redesign.
   RESOLVED: enrich_nodes() now raises ValueError on an UNKNOWN contract_id or
   doc_type (naming the offending pdf_source) instead of writing the sentinel.
   Because build_nodes() -> enrich_nodes() runs inside `make build`, an
   underivable source now fails LOUD at ingest, not only under `make check` —
   matching the loader's fail-loud posture. Verified: make check still passes
   (all 401 nodes classify; no false raise).

F3 - LOW (robustness) [RETAINED — acceptable as-is]: DOC_TYPE_KEYWORDS relies on
   3-char substrings + order.
   "roa", "coa", "noa", "ntp", "ads" are matched as bare substrings anywhere in
   the filename (enrich.py:38-47). Correct for all 18 current sources
   (verified), and the "full-form before abbreviation" ordering is documented
   and load-bearing. But it is fragile to plausible future names ("...road...",
   "...approval..." would false-match ROA/NOA before reaching the right key).
   Given the config-driven, small-corpus constraint this is acceptable AS-IS --
   flagging as latent only. If ever hardened, anchor to the token following the
   contract id rather than a free substring.
   HANDOVER (deliberately NOT changed): kept as-is under the small-corpus,
   config-driven constraint — all 18 current sources classify correctly and the
   full-form-before-abbreviation ordering is load-bearing. SOLUTION IF IT EVER
   BITES (a future name like "...road..."/"...approval..." false-matching
   ROA/NOA): stop free-substring matching in doc_type_from_source (enrich.py:61)
   and anchor the keyword to the filename token immediately following the
   contract id, so only the doc-type slot is inspected. Small, local change; do
   it only when a real source breaks, not pre-emptively.

F4 - LOW (assumption) [FIXED]: reading-order y-axis origin is unverified.
   _reading_order_key sorts (page, y, x) ascending and calls it "top-to-bottom"
   (relationships.py:20-22). Confirmed coordinate[0]~=X (1-725),
   coordinate[1]~=Y (9-821), so the axis assignment is right. But ascending-y =
   top-to-bottom ONLY if the origin is top-left. These are image-space coords
   (imageSource present in the schema), which conventionally are top-left, so it
   almost certainly holds -- but it is an unverified assumption, and if the OCR
   emitted PDF-native bottom-left coords the order silently inverts. Also no
   tie-break for same-line chunks (OCR y-jitter) and no multi-column handling.
   Impact today is NIL because of F1 (nobody reads the order) -- but if F1 is
   resolved by wiring it up, F4 becomes real and should be checked first.
   RESOLVED (F1 now consumes the order, so this was made real):
   - Origin CHECKED: coordinates are image-space (imageSource in schema), origin
     top-left, observed y range ~9-821 growing downward, so ascending y IS top-
     to-bottom. Documented in the _reading_order_key comment; the assumption
     holds, no inversion.
   - Same-line tie-break ADDED: the corpus has 48 consecutive chunk pairs on the
     same visual line (y-gap <5px; 20 at <1px) while real line spacing is ~51px,
     so raw (page, y, x) ordered same-line chunks by y-jitter, not left-to-right.
     _reading_order_key now quantises y to a 10px band — return (page,
     round(y/_LINE_BAND), x) — so a visual line groups and orders by x, and the
     band (10px) is far below line spacing (~51px) so it never merges adjacent
     lines. Verified via the make check reading-order eyeball chain.
   - Multi-column: still unhandled (out of scope, no multi-column source today);
     the left-to-right tie-break reads across columns, acceptable at this corpus.

F5 - NIT [FOLLOWED]: pdf_page is stored as a string ("1") and only cast via
   int() inside the sort key (relationships.py). Fine, but any future numeric
   comparison on metadata["pdf_page"] must remember it is a string.
   DONE: recorded the string-storage caution as an inline NB comment at the
   _reading_order_key cast so the next numeric use of pdf_page is warned. No
   behavioural change (the existing int() cast was already correct).

F6 - NIT [NOTED]: enrich_nodes and link_reading_order both mutate in place AND
   return the list (dual contract). Documented and consistent between the two;
   harmless.
   NOTE (no change): left as-is by design — the dual mutate-and-return contract

   place mutation; returning the list is a convenience only. If a future refactor
   ever splits these, pick one contract (return-new OR mutate-in-place) rather
   than keeping both. Not worth touching now.

ISSUES, BY SEVERITY
-------------------

F1 - HIGH (coupling) [FIXED — pinned by test]: two independent signatory parsers
   must agree, maintained separately.
   index.py has _CONTEXT_LINE_RE + _person_from_chunk (index.py:28-57) to BUILD
   the per-contract signatory_summary node. verify.py has a DIFFERENT extractor,
   _extract_sig_names (verify.py:68), which generate._build_person_names
   (generate.py:48-63) uses to decide which signatory names an answer may
   legitimately contain. So one parser produces the summary and a different
   parser polices answers derived from it. If they drift, the verifier can
   reject a correct signatory answer (a name the summary lists but the verifier
   won't accept), or bless one the summary omits. This is real cross-module
   coupling with no shared implementation or test pinning them together. The
   parser lives in this partition (index.py); the consumer is Partition 4
   (verify/generate). Consolidate to one signatory extractor imported by both,
   or add a test asserting the two agree over database/ signature chunks.
   RESOLVED: took the TEST fork (consolidation was wrong — the two functions have
   different shapes/goals: one returns (name,title) pairs to build the summary,
   the other a name set to police answers). rag/verify.py gained a __main__ pin,
   wired into scripts/check.sh, that builds the summaries via
   index._signatory_summaries and asserts _extract_sig_names recovers every listed
   name over the real database/ chunks. Verified: make check → "6 signatory
   summaries, 34 listed names all recoverable". NB the drift is latent today
   (signature names are all-caps, which both parsers agree on); the pin now fails
   loudly the moment a builder-emitted name the policer can't ground appears.

F2 - MEDIUM (integrity) [FIXED]: manifest JSON-parse failure silently degrades a
   whole contract to "not stated", which coverage.py then misreports as a DATA ceiling.
   _parse_extraction (manifest.py:111-124) matches `\{.*\}` (greedy, DOTALL) and
   on any json.JSONDecodeError falls back to ALL fields = "not stated" with the
   error swallowed (bare `pass`). Consequence: a model/parse failure is
   indistinguishable from genuinely-absent OCR data. coverage.py exists
   precisely to separate a DATA ceiling ("field never in the source") from a
   MODEL ceiling ("model didn't reach it") -- but a parse failure lands in the
   DATA bucket and reads as "not extractable", defeating that distinction. The
   greedy brace regex also over-captures if the model emits prose+JSON+prose.
   Fix: log/surface a parse failure distinctly from an honest "not stated" (even
   a stderr warning + a count in the build output) so coverage's ceiling stays
   trustworthy.
   RESOLVED: _parse_extraction now returns (record, parsed_ok); build_manifest
   prints a per-contract stderr WARNING and a final "N/total failed to parse"
   count when a reply carries no parseable JSON, so a parse failure is visibly
   distinct from an honest "not stated". The greedy \{.*\} was also tightened to
   non-greedy \{.*?\} so a prose+JSON+prose reply captures just the object.
   Verified (model-free): good/broken/no-brace/prose+object inputs classify
   correctly.

F3 - MEDIUM (build robustness) [FIXED]: the manifest step has no resume/idempotency.
   build_manifest (manifest.py:127-150) loops sorted(by_contract) issuing one
   llm.complete() per contract and only persists after ALL succeed. It runs as
   the LAST of three separate processes (build.sh:13), AFTER the expensive CPU
   embed. Any Ollama hiccup on contract k discards the k-1 completed extractions
   and forces a full rerun of every contract. (verdict.txt covers the SCALE
   angle -- days/weeks at 16k-100k; this is the plain-robustness angle that
   already applies at 6.) Minimal mitigation: write each record incrementally /
   skip contracts already present in manifest.json, so a rerun resumes instead
   of restarting. Also note load_nodes/enrich run in all three processes and
   build_nodes runs again inside build_manifest -- cheap (pure Python), so not
   worth changing, but it means the node prep is recomputed 3x.
   RESOLVED: build_manifest now persists each record as it completes and RESUMES
   from a partial manifest.json (fewer contracts than the corpus) — reusing the
   done records and re-extracting only the missing ones. A COMPLETE manifest is
   ignored, so a normal rebuild still re-extracts fresh (prompt/field changes take
   effect; `make clean` / deleting manifest.json also forces a clean build).
   Verified (model-free, stub LLM): a partial manifest resumed with only the
   missing contracts extracted; a complete manifest re-extracted all. The 3x
   node-prep recompute is left as-is (cheap pure Python, as noted).

F4 - LOW (latent) [FIXED]: pdf_page is string-sorted in the extraction input.
   _extraction_input sorts by (doc_priority, pdf_page) with pdf_page a string
   (manifest.py:67-68). Harmless today -- verified max page is 4, so lexical ==
   numeric. At >=10 pages, page "10" sorts before "2", reordering the lines fed
   into the 3000-char budget and possibly truncating identity content. Same
   root as Partition-1 F5 (pdf_page stored as str). Cast to int in the sort key.
   RESOLVED: _extraction_input sort key now casts int(n.metadata["pdf_page"]), so
   pages order numerically (1,2,10) not lexically (1,10,2). Verified (model-free)
   with a synthetic 10-page input. One-line change, mirrors Partition-1 F4.

F5 - LOW [DOCUMENTED — kept as-is]: index.py's smoke test hard-codes a
   model-specific assertion.
   __main__ asserts the top hit for a "Tabang River" query is 24CC0265
   (index.py:147-157). Fine as a persistence smoke test on the default embed
   model, but it is coupled to a specific model's ranking -- swapping
   RAG_EMBED_* (the config-driven selling point) could fail this assertion even
   when retrieval is healthy. It's a self-check, not the recall gate, so low
   impact; just don't read a failure here as a retrieval regression without
   re-checking `make eval`.
   DOCUMENTED (deliberately NOT changed): the assertion is a persistence smoke
   test, not the recall gate, and hard-failing on a legit model swap is a smaller
   harm than losing the smoke test. Added an NB comment at index.py:158 spelling
   out that a failure after an RAG_EMBED_* swap must be confirmed against
   `make eval` before it counts as a regression. No behavioural change.

F6 - NIT [FIXED]: synthetic summary nodes get a random id_ each build.
   _signatory_summaries emits TextNode(...) with no id_ (index.py:99-110), so
   LlamaIndex assigns a fresh UUID every build -- the index isn't byte-repro-
   ducible across rebuilds for these nodes. Harmless (eval ground truth is real

   embedded and retrievable, so they can compete with real chunks in top-k
   (a retrieval-quality question for Partition 3, flagged here only because they

   RESOLVED: _signatory_summaries now sets a deterministic id_
   (f"{cid.lower()}_signatories_summary", the same key as pdf_source) instead of

WHAT'S GENUINELY WELL-BUILT (KEEP)
----------------------------------

- RerankingRetriever (rerank.py:25-46) is a clean BaseRetriever wrapper: it
  plugs straight into RetrieverEvaluator and carries an optional QueryTrace seam
  where recall (candidates) and precision (survivors) are both visible. Small,
  composable, correct.
- The three-mode ablation (baseline/filtered/rerank) is the right way to show
  each stage's contribution, and the runner prints a per-type breakdown plus an

- `empty` items are correctly excluded from recall scoring (evaluate.py:46-47):

ISSUES, BY SEVERITY
-------------------

F1 - MEDIUM-HIGH (eval validity) [FIXED]: the recall gate uses the GROUND-TRUTH
   contract_id for the filter, so it never tests the production resolver.
   evaluate.py injects item["contract_id"] straight into the MetadataFilter
   (evaluate.py:50-56). But in production, generate.route() DERIVES the
   contract_id from the question text (explicit id, else _resolve_contract_ids
   token matching, else None) -- see Partition 4. So `make eval` measures
   retrieval GIVEN a perfect filter; it does not measure retrieval as users
   experience it, where the filter is inferred from natural language and can
   resolve to the wrong contract or to None (unfiltered). The headline
   "hit_rate 1.000" is therefore CONDITIONAL on perfect routing, and the router
   -- the component most likely to misfire on a real question -- is outside the
   gate. This is the same silent-divergence theme as P1/P2: the thing that can
   break is not the thing being measured. Add a resolver-level check (route the
   `query` and assert it yields the expected contract_id) so the gate covers the
   NL-to-filter step, not just retrieval past it.
   RESOLVED: added resolver_check() + a resolver GATE printed before the retrieval
   eval. It routes each item's human `query` through the SAME resolver production
   uses (route_contract_id, now module-level in generate.py) and asserts it yields
   the item's contract_id (None for cross-contract broad/complex); a mismatch
   sys.exits non-zero. Model-free (manifest + resolver, no LLM), so it stays inside
   the no-Ollama gate. Verified: 40/40 queries resolve to the correct filter.

F2 - MEDIUM (eval validity) [FIXED]: broad/complex hit_rate is "any expected chunk
   in top-k", which overstates what those questions need.
   For a broad probe like all_district_engineers (6 names across 6 contracts,
   build_retrieval_eval.py:95-97), retrieving ONE of the six scores hit_rate=1.
   So broad/complex reading 1.000 does NOT mean the corpus-spanning answer was
   fully retrieved -- only that at least one anchor was. The code comment admits
   this ("reads high by construction", evaluate.py:88-89). In practice the real
   broad-answer path is the injected manifest / signatory summaries (Partition 2),
   NOT top-k retrieval of all six chunks -- which is fine, but then these rows
   are weak retrieval probes that mainly pad the blended headline. Either score
   broad/complex by per-anchor recall (did all N appear?) or label them clearly
   as non-gating.
   RESOLVED: added a per-anchor COVERAGE column (_anchor_coverage =
   |retrieved ∩ expected| / |expected|) to the per-row table and the per-type
   summary, and labelled broad/complex "[lenient: any-hit; coverage = full-answer
   recall]". The gap is now visible, e.g. broad all_winning_bidders reads
   hit_rate=1.00 but coverage=0.02 (top-k retrieves ~1 of many anchors; the real

Verified: _GEO_STOP is defined TWICE identically in verify.py and nothing uses
the first copy; the agent reuses RagAnswerer._verifier (so the person tier is

WHAT'S GENUINELY WELL-BUILT (KEEP)
----------------------------------

- The two-tier verifier is a genuinely good design and clearly documented:
  BLOCK (DERIVED, zero false positives -- invented contract id) vs FLAG
  (EXTRACTED, withhold-on-doubt -- mis-bound location/contractor/person). The
  check_bindings=False escape hatch (verify.py:183-184) correctly spares the
  analytical route from the single-contract assumption.
- The resolver/verifier symmetry is elegant: the SAME _GEO_STOP + >=4-char guard
  gates a token on the way IN (generate._resolver_index) and on the way OUT
  (verify._location_index), so "distinctive" means one thing in both directions.
- _norm diacritic stripping (generate.py:67-71) is correct and well-motivated
  ("macanao" must match "macañao"), and shared across resolver and verifier.
- trace.py is a strong, truly zero-cost diagnostic: disabled it opens no file and
  returns immediately (trace.py:81-84); stage-of-death pinpoints retrieval-miss
  vs rerank-drop vs grounding from gold-chunk survival. Records ids/scores/meta,
  never text or vectors -- machine-diffable and quiet.
- _extract_sig_names is shared by the verifier and generate._build_person_names
  -- the RIGHT pattern (contrast the separate index.py summary parser, P2-F1).


ISSUES, BY SEVERITY
-------------------

F1 - MEDIUM (dead code): _GEO_STOP is defined twice, identically, in verify.py.
   Lines 36-41 and 86-91 are byte-identical, and nothing between them references
   the name (_extract_sig_names, the only code in that span, does not use it), so
   the FIRST definition is immediately shadowed and dead. generate.py imports
   _GEO_STOP and gets the second. Pure duplication -- delete the first copy (or
   the second and move the survivor above _extract_sig_names). Straight
   Simplicity/Surgical cleanup; /simplify would flag it.

F2 - MEDIUM (hidden contract): RagAnswerer.verify() depends on state set only by
   answer().
   answer() stashes self._trace (generate.py:217) and verify() reads it
   (generate.py:226). So verify() raises AttributeError if called after
   answer_once() or standalone. Live callers are safe today -- chat.py and
   __main__ call answer() then verify(); the agent uses _verifier.check()
   directly and never touches RagAnswerer.verify(). So this is latent fragility,
   not a live bug: a public method with an unstated ordering requirement and a
   crash (not a no-op) if violated. Either make verify() accept the response's
   own trace, or guard self._trace with a default so it degrades to no-trace.

F3 - LOW-MEDIUM (silent tier loss, latent): the person-fabrication check is
   silently skipped when person_names is absent.
   check() only runs the person tier `if self._person_owners` (verify.py:209),
   which is empty unless the constructor was given person_names. Production is
   fine (generate builds and passes the map; the agent reuses that verifier), so
   this is latent -- but a Verifier built without the map (a test, a future
   caller) silently loses an entire grounding tier with no signal. Note this is
   distinct from the analytical route's check_bindings=False, which is an
   intentional, documented skip.

F4 - LOW-MEDIUM (chained blind spot): the verifier oracle inherits manifest
   extraction gaps.
   _contractor_index skips any contract whose contractor is empty/"not stated"
   (verify.py:129-131). So a contract whose contractor failed LLM extraction --
   including the SILENT parse-failure fallback flagged in P2-F2 -- has no token
   in the index, and the verifier can never flag a mis-binding involving that
   contractor. A manifest extraction miss thus silently widens the verifier's
   blind spot. Not fixable here (fix at the manifest, P2-F2), but worth recording
   as a cross-partition consequence: the grounding check is only as complete as
   the manifest it trusts.

F5 - LOW (doc/impl divergence): stage_of_death promises a verdict it never
   returns.
   The docstring lists "generation" as a possible verdict (trace.py:10, 107) but
   no branch produces it -- the generate stage is never gold-checked (its emit
   passes no nodes=, generate.py:207-209), so gold survival through synthesis is
   invisible and the code only ever returns no-gold/retrieval-miss/rerank-drop/
   grounding/ok. Either drop "generation" from the docs or emit gold-bearing
   nodes at the generate stage so the verdict can actually fire. Same silent-
   divergence theme as the other partitions.

F6 - LOW (efficiency, scale-adjacent): the FLAG and person checks scan every
   corpus location/contractor token per attribution unit / sentence with a regex
   each (verify.py:187-234), and _build_person_names scans the whole docstore on
   every RagAnswerer() construction (generate.py:56-63). Fine at 6 contracts;
   verdict.txt owns the 100k angle.

F7 - NIT: the BLOCK tier's CONTRACT_ID_RE.findall can match an id embedded in a
   longer digit run (e.g. inside "124CC02650"); and trace query_id is a 12-hex
   truncation of sha1(question+timestamp), so two identical questions in the same
   instant collide and the second overwrites the first trace file. Both negligible.


BOTTOM LINE
-----------

The verifier design and the tracer are the strongest work in the codebase so far
-- keep them. The only clean-cut fix is F1 (delete the dead duplicate _GEO_STOP).
F2 and F3 are latent hidden-contract / silent-tier risks that production happens
to avoid but that will bite a future caller. F4 and F5 are the recurring silent-
divergence theme again: the verifier trusts a manifest that can fail quietly,
and the tracer documents a verdict it can't emit.

One theme dominates every partition: SILENT DIVERGENCE -- two things that must

  P2-F1  two signatory parsers (summary builder vs verifier) that must agree.

  P5-F1  the agent eval prints a route label it never checks; 2 routes untested.
  P6-F1  the streaming pipeline is a copy of the agent that has already diverged.

The codebase's STRENGTH is the inverse: wherever there is ONE source of truth, it
is excellent -- the two-tier verifier, the deterministic router, the zero-cost
tracer, the honest "not stated" data posture, coverage.py importing the field list
from manifest. The through-line fix is not more code but fewer copies: one
signatory parser, one retrieval-construction path, one agent orchestration with
streaming as an aspect, and evals that assert the component (routing, resolver)
rather than only the final text. Scale is out of scope here and fully owned by
verdict.txt; nothing above depends on corpus size.
